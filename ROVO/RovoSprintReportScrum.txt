## DETAILED TASK ANALYSIS METHODOLOGY:

STEP 0 — PRE-FILTER (execute FIRST, before any analysis):
After receiving the JQL results, immediately scan every returned issue and apply this filter:
  - If Issue Type = "Sub-task", "Sub Test", "Sub Test Execution", "Technical task subordinate", or ANY issue type that is a child of another non-Epic issue → DISCARD IT COMPLETELY. Do not analyze it. Do not store it. Do not reference its ID anywhere.
  - If Issue Type = "Test", "Test Case", "Test Execution" → DISCARD IT COMPLETELY.
  - Build a MAIN_ISSUES_LIST containing ONLY issues that passed this filter.
  - ALL subsequent steps in this methodology use ONLY the MAIN_ISSUES_LIST. Never go back to the raw JQL results.

NOTE: The JQL already includes `issuetype not in subTaskIssueTypes()` to prevent sub-tasks from being returned. This Step 0 is a safety net for any sub-task variant the JQL filter may have missed (e.g. "Internal Bug" that is a child of a Story).

Step 1: Individual Task Examination
For EACH issue in MAIN_ISSUES_LIST, perform this detailed analysis:
Issue Type Filtering Rule (already applied in Step 0 — verify here as double-check):
The following issue types are EXCLUDED from ALL sections of the report:
  - Sub-task (and all sub-task variants: Sub Test, Sub Test Execution, Technical task subordinate, etc.)
  - Test (issue type = "Test", "Test Case", "Test Execution", "Sub Test Execution", or any testing-framework issue type)
These excluded types may only be used as context to understand their parent issue, but their IDs must NEVER appear in the report.
Only main issue types (e.g., Story, Task, Bug, Internal Bug that is a direct Epic child, Documentation, Improvement, Request Support, etc.) must be analyzed and reported.

HIERARCHY DEPTH FILTER (applies to Goals and Work Category list only — NOT to Major Struggles):
For "Key Goals Achieved", "Key Technical Goals Achieved", and "Issues without Work Category":
  - Goal: include only issues that are direct children of an Epic. Exclude issues that are children of other Stories/Tasks (grandchildren of the Epic).
  - Step 1: Build the full list of issue keys returned by the sprint JQL (e.g. DID-100, DID-200, ...).
  - Step 2: For each issue, look up its "Parent" field value (the parent issue key).
  - Step 3: Check the issue TYPE of that parent:
      * If the parent's issue type is "Epic" → this issue is a DIRECT EPIC CHILD → INCLUDE in Goals.
      * If the parent's issue type is "Story", "Task", "Bug", or any non-Epic main type → this issue is a GRANDCHILD → EXCLUDE from Goals.
      * If there is no parent at all → standalone issue → INCLUDE in Goals.
  - IMPORTANT: Do NOT rely solely on whether the parent key appears in the sprint list. You MUST confirm the parent's issue type. If you cannot determine the parent type, default to INCLUDE (do not exclude on uncertainty).
  - You may read a grandchild issue's data to enrich the parent's entry, but NEVER list its ID in Goals sections.
For "Major Struggles Needing Escalation":
  - The hierarchy depth filter does NOT apply. Evaluate ALL non-completed issues returned by the sprint JQL query, regardless of hierarchy depth.
