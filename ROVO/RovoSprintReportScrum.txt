## DETAILED TASK ANALYSIS METHODOLOGY:

Step 1: Individual Task Examination
For EACH task returned by the JQL query, perform this detailed analysis:
Issue Type Filtering Rule (Main tasks only):
The following issue types are EXCLUDED from ALL sections of the report (Key Goals Achieved, Key Technical Goals Achieved, Major Struggles Needing Escalation, and Issues without Work Category):
  - Sub-task (and all sub-task variants: Sub Test, Sub Test Execution, Technical task subordinate, etc.)
  - Test (issue type = "Test", "Test Case", "Test Execution", "Sub Test Execution", or any testing-framework issue type)
These excluded types may only be used as context to understand their parent issue, but their IDs must NEVER appear in the report.
Only main issue types (e.g., Story, Task, Bug, Documentation, Improvement, Epic, Request Support, etc.) must be analyzed and reported.

HIERARCHY DEPTH FILTER (applies to Goals and Work Category list only — NOT to Major Struggles):
For "Key Goals Achieved", "Key Technical Goals Achieved", and "Issues without Work Category":
  - After retrieving all sprint issues via JQL, build the list of issue keys returned (e.g. DID-100, DID-200, etc.).
  - For each issue, check its "Parent" or "Parent Link" field to get the parent issue key.
  - GRANDCHILD RULE: If the parent key of an issue IS itself in your sprint issue list, then this issue is a grandchild (its parent is a Story/Task/Bug in the sprint, not an Epic). EXCLUDE it from Key Goals, Key Technical Goals, and Issues without Work Category.
  - DIRECT CHILD RULE: If the parent key is NOT in your sprint issue list (or there is no parent), the issue is a direct Epic child or standalone. INCLUDE it in these sections (subject to status and Work Category rules).
  - You may read a grandchild issue's data to enrich understanding of its parent, but NEVER list its ID in Goals sections.
  - Rationale: Epics are not assigned to sprints as active issues, so a parent that appears in the sprint results is always a Story/Task/Bug — making the child a grandchild of the Epic.
For "Major Struggles Needing Escalation":
  - The hierarchy depth filter does NOT apply. Evaluate ALL non-completed issues returned by the sprint JQL query, regardless of hierarchy depth. If an incomplete issue is in the sprint, evaluate it for escalation.

A. Task State Classification:
COMPLETED (Done, Closed, Resolved): ELIGIBLE for "Key Goals Achieved" and "Key Technical Goals Achieved" sections ONLY.
IN PROGRESS (In Progress, In Development, Review, To Test, Test In Progress, To review & Approval): NEVER include in Goals sections. Evaluate for "Major Struggles" — review comments for escalation signals.
BLOCKED (Blocked, Waiting, On Hold): NEVER include in Goals sections. IMMEDIATE escalation candidate for "Major Struggles".
NOT STARTED (To Do, Open): NEVER include in Goals sections. Evaluate for "Major Struggles" if worked on during the sprint.

CRITICAL STATUS RULE: "Key Goals Achieved" and "Key Technical Goals Achieved" MUST contain ONLY issues whose status is DONE, Closed, or Resolved at the time of the report. Issues in any other status (In Progress, Review, Blocked, To Do, etc.) are STRICTLY FORBIDDEN in these two sections, regardless of their Work Category.

B. Task Content Deep Dive:
Read and understand each task by examining Summary, Description, Comments, Subtasks, Custom Fields, and Labels/Components.

C. Business vs. Technical Classification Decision Tree:

IMPORTANT: When referring to 'WORK CATEGORY', always use the EXACT value of the Jira custom field named "Work Category" on each issue.
Never invent, infer, or guess a work category from the summary, description, labels, components, or issue type. If the Jira "Work Category" field is empty or missing, treat it as "no work category" following the rules below.

Classify as "Key Goals Achieved" if ALL of the following are true:
  1. STATUS = DONE / Closed / Resolved (mandatory — incomplete issues are EXCLUDED)
  2. Issue type is a main type (Story, Task, Bug, etc.) — sub-tasks EXCLUDED
  3. Work Category is exactly one of:
     - Client Services
     - Product:Feature
     - Product:Discovery
     - Deprecation
Mandatory Exclusion: DO NOT include tasks with any other Work Category, tasks with empty Work Category, tasks NOT in Done/Closed/Resolved status, or sub-task issue types. 
 * En este reporte SOLO se deben considerar y mostrar issues principales, por ejemplo:
        * Story, Task, Bug, Documentation, Improvement, Epic, etc.
    * Aunque puedan existir tipos como Sub-Task, Sub-Test, Internal Bug, Sub Test Execution, Technical task, u otros tipos subordinados:
        * Esos tipos nunca deben aparecer en el reporte.
        * Pueden usarse internamente como contexto para entender el trabajo, pero no se mencionan ni se listan en ninguna sección.

Tasks where the 'WORK CATEGORY' field is empty must be mentioned in a separate list after the analysis, using the format: [ISSUE-ID] - empty

Classify as "Key Technical Goals Achieved" if ALL of the following are true:
  1. STATUS = DONE / Closed / Resolved (mandatory — incomplete issues are EXCLUDED)
  2. Issue type is a main type (Story, Task, Bug, etc.) — sub-tasks EXCLUDED
  3. Work Category is exactly one of:
     - Enabler
     - Technical Debt
     - Quality Assurance
     - Quality:L3 Support
     - L3 Support
     - Risk Mitigation
     - Team Management
     - SysOps/DevOps
Mandatory Exclusion: DO NOT include tasks with any other Work Category, tasks with empty Work Category, tasks NOT in Done/Closed/Resolved status, or sub-task issue types. Tasks where the 'WORK CATEGORY' field is empty must be mentioned in a separate list after the analysis, using the format: [ISSUE-ID] - empty.

Classify as "Major Struggles Needing Escalation" — evaluate ALL main issues (no sub-tasks) that were NOT completed during the sprint using this priority:
  PRIORITY 1 — IMMEDIATE ESCALATION: Status is Blocked, Waiting, or On Hold.
  PRIORITY 2 — ESCALATION CANDIDATE: Status is In Progress, In Development, Review, To Test, or To review & Approval — read comments and activity history to identify: explicit blockers mentioned, requests for help, missed deadlines, dependency delays, or risk signals.
  PRIORITY 3 — MONITOR: Status is To Do or Open but the issue was worked on during the sprint (has comments or activity) — review comments for context.
  EXCLUDE: Issues with no sprint activity and no comments. EXCLUDE all sub-task issue types.
For each escalation candidate: suggest a concrete action plan based on the comments and current status. Identify owner, specific ask, and recommended due date.

For Key Goals Achieved (DONE issues only - Work Category: Client Services, Product:Feature, Product:Discovery, Deprecation):
   - Status Filter: ONLY include issues in Done / Closed / Resolved. SKIP any issue not in these statuses.

   - Issue Listing: After the achievement summary, list the Task IDs included.

For Key Technical Goals Achieved (DONE issues only - Work Category: Enabler, Technical Debt, Quality Assurance, Quality:L3 Support, L3 Support, Risk Mitigation, Team Management, SysOps/DevOps):
   - Status Filter: ONLY include issues in Done / Closed / Resolved. SKIP any issue not in these statuses.
   - Sub-task Filter: NEVER include sub-task issue types. Use sub-task data only to enrich the parent issue analysis.
   - Grouping Rule: Group by Epic or Component. If no Epic, group under the relevant technical area.
   - Analysis Rule: For each group, write a 1-2 sentence summary explaining the technical capability enabled, risk reduced, or quality improvement achieved - use issue summaries, descriptions and comments.

   - Sub-task Filter: NEVER include sub-task issue types.
   - Priority 1 - IMMEDIATE: Status = Blocked / Waiting / On Hold - always include.
   - Priority 2 - CANDIDATE: Status = In Progress / In Development / Review / To Test - read comments for blocker signals, missed deadlines, cross-team dependencies, or explicit risk mentions.
   - Priority 3 - MONITOR: Status = To Do / Open with sprint activity - read comments for context.
   - For each escalation item: (a) describe the business/delivery risk, (b) suggest a concrete action plan based on comments and current state, (c) identify owner, specific ask, and recommended due date.

   - If no escalation candidates exist: write "No major struggles requiring management escalation at this time."

## GLOBAL HARD FILTERS (NON-NEGOTIABLE):
- You MUST NEVER mention, list, or output any issue whose Jira Issue Type is "Sub-task" (or any sub-task variant) in ANY section of the final report. Sub-tasks are ONLY context for their parent issues.

A grandchild is an issue whose parent key also appears in the sprint JQL results (meaning the parent is a Story/Task/Bug in the sprint, not an Epic). EXCEPTION: grandchild issues that are NOT completed MUST still be evaluated for "Major Struggles Needing Escalation" — incomplete issues of any hierarchy depth must be escalated if they represent a delivery risk.
- You MUST NEVER include any issue whose 'WORK CATEGORY' is "Risk Management" in the "Key Goals Achieved" or "Key Technical Goals Achieved" sections. "Risk Management" is not an allowed category for achievements.
